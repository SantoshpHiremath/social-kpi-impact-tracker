# Social KPI & Departmental Impact Tracker

A real, tested Python pipeline that tracks progress on a workplace-accessibility/inclusion initiative and links its social KPIs to departmental performance — built specifically to close the "Quantify Social Responsibility (CSR) Impact" task named in Airbus Helicopters' "Intern Data Scientist - Engineering Strategy & Make-or-Buy Optimization" posting: "develop and maintain tracking tools to measure the progress of the 'Disability Friendly Company' initiative, linking social KPIs to overall departmental performance."

## What this is

A pipeline that generates realistic, quarterly, per-department accessibility/inclusion data (workforce representation, workplace-accommodation requests and completions, accessibility-training completion), validates it for real data-quality problems, computes progress KPIs, explicitly joins those KPIs to departmental performance metrics (on-time delivery, employee engagement, voluntary attrition) by department and quarter, and writes everything into a real, formatted, multi-sheet Excel tracking report.

**All department names, headcounts, and metrics are entirely fictional**, generated by `src/data_sources.py`. This is not real Airbus, Airbus Helicopters, or any company's actual workforce or accessibility data. The point of this project is to demonstrate the tracking-and-linkage method a CSR-impact tool needs, not to present real company data.

## Why this exists

The posting names a specific, unusual task most data-portfolio projects don't touch: building a tool that tracks a social-responsibility program's progress and connects it, credibly, to departmental performance — not just reporting a headline number, but joining program KPIs to operational metrics by department and time period so leadership can see whether the two move together. That join has to be done carefully (matching department and quarter exactly, not just concatenating two tables), and the underlying program data has to be validated first, since accessibility/HR data has its own realistic failure modes (a completions count that's higher than the requests count because of a reporting carryover error, or a training metric a department simply hasn't reported yet for the current quarter).

## What it actually does

- **`src/data_sources.py`** — generates synthetic quarterly accessibility/inclusion records across 6 fictional departments and 6 quarters, plus separate departmental performance records. Deliberately injects two realistic problems: one record where completed workplace accommodations exceed requested accommodations in the same quarter (a real, recurring data-entry error — completions carried over from a prior quarter miscounted into the wrong period), and one record with a missing training-completion percentage (a metric not yet reported by that department for that quarter, not something to silently treat as 0%).
- **`src/data_quality.py`** — flags both injected problem types before any KPI gets computed from them: accommodation overcounts and missing training metrics.
- **`src/kpi_linkage.py`** — computes the accessibility-program progress KPIs (workforce representation %, accommodation fulfillment %, training completion %), explicitly excludes flagged overcount rows from the fulfillment-rate calculation (a rate above 100% isn't a meaningful KPI to report), and joins the result to departmental performance records via an explicit `(department, quarter)` key — not a positional zip, so a missing or mismatched quarter is skipped rather than silently paired with the wrong data. Also produces a per-department quarter-over-quarter trend view, since a real leadership report needs progress over time, not just a snapshot.
- **`src/report.py`** — writes a real, formatted `.xlsx` workbook (via `openpyxl`) with three sheets: Summary, Accessibility & Performance (the linked view), and Data Quality Flags.
- **`run_pipeline.py`** — runs the full flow end to end and prints a real console report (see sample output below, copied from an actual run).

## Verification

33 automated tests (`tests/`), all passing, covering: data generation (reproducibility — including a real bug found and fixed in the reproducibility test itself, since `NaN != NaN` in Python and the naive dataclass-equality check failed on the deliberately-injected missing-metric row even though the data was genuinely identical; the fix compares fields individually with a NaN-aware check), data-quality flagging (correctly flags both injected issues and nothing else), KPI computation (representation and fulfillment percentages, including the divide-by-zero and overcount edge cases), the department/quarter join (correctly matches, and correctly skips unmatched department/quarter combinations rather than fabricating a pairing), the trend view, and the Excel report itself (real file is created, contains the expected sheets, and the data in each sheet matches the input).

```bash
python3 -m pytest -v      # 33 tests, all passing
python3 run_pipeline.py   # runs the full pipeline, writes output/social_kpi_impact_report.xlsx
```

## Honest limitations

- All data is synthetic — no real workforce, accessibility, HR, or departmental-performance data is used or implied.
- This does not model any real "Disability Friendly Company" program specifically (Airbus's or anyone else's) — it models the general shape of workplace-accessibility program tracking, based on publicly-understood CSR reporting concepts (representation, accommodation fulfillment, training completion), not internal knowledge of any real program's structure.
- The correlation between accessibility-program maturity and departmental performance in the synthetic data is loosely modeled for realism, not a claim about any real causal or statistical relationship between the two in practice.
